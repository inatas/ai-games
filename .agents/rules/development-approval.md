# 开发方案确认与实施门禁

适用范围：新增功能、需求调整、方案审阅、开发实施或续做，以及发现提前实现时的处理。框架和所有MOD均适用。只读查询、普通Git同步、纯排版或失效链接修复无需加载；任务转为功能开发时须先读取本规则。

所有新增功能及对现有需求的调整，必须先更新对应`.agents/note`与设计、接口、数据及验收测试文档，再提交用户审阅。只有用户明确确认该版本及范围后，才能生成或修改实现代码、可执行测试、数据库迁移和部署配置。文档中的建议不等于已获确认；不能以实现简单、可逆或顺手修复为由跳过此流程。

确认前可以检查现状、编写文档和测试用例说明、运行文档检查，不得开始功能实现。note必须记录“待确认”或用户确认的版本与范围；需求发生变化时，受影响部分重新走此流程。既有确认继续覆盖未变化的范围，不重复索取确认。纯排版和失效链接修复不属于需求调整。

本规则由用户明确要求。每次提交审阅说明具体文件、待确认范围和仍未实现的内容；确认后按批准文档先写行为测试，再实现并验证。

## 开发文档与确认记录

开始开发前，必须先在需求所属的`.agents/note`创建或完善开发文档：框架公共能力归根目录，MOD能力归`mods/<mod>/.agents/note`。每项新的独立 feature 使用新的序号 note；同一 feature 的修订和续做更新原 note，不为每次开发回合重复建文件。note是开发入口，不能只在聊天、代码注释或其他docs中写计划后直接编码。设计、接口、数据与验收正文按架构主题更新已有 docs；仅在现有文档确无合适归属时新建 docs，不按 feature 默认另建一套专题 docs。

提交审阅的开发文档必须明确：

- 方案版本、目标、本次实施范围与明确不包含的内容。
- 拟新增或调整的模块职责、接口、数据结构、状态流转；涉及权限、事务、幂等、恢复或部署时说明对应约束。不涉及的项目可注明不适用。
- 行为与边界验收用例、验证方式、实施顺序，以及仍需用户裁定的问题。确认前只写测试用例说明，不生成可执行测试。
- 当前状态为“待确认”；获得确认后记录用户确认的版本、范围和原话或可核对的会话依据。详细正文可链接到所属docs，不重复维护两份协议。

## 规则确认不等于开发方案确认

用户对游戏规则、产品行为、架构方向或个别问题的裁定，只确认对应需求事实，不自动批准尚未审阅的模块拆分、接口、数据结构、状态机、测试实现或接入方案。不得把“规则已确认”写成“开发方案已确认”，也不得自行记录超出用户表达的授权。

“next”“继续”“continue”“开始下一步”等续做指令，只能推进当前已明确确认的开发方案范围。若当前只有规则确认、尚未提交开发方案，下一步就是完善文档并提交审阅；若方案仍标为待确认，续做不能代替对该版本及范围的明确批准。用户明确表示按已提交的某版本或本次具体范围实施时，才记录为开发确认。

已批准方案中未变化的实现步骤无需逐模块重复审批；但新增加的能力、接口、数据或行为不因被称为“下一阶段”“内部实现”“纯函数”“测试草稿”或“不依赖待确认接口”而自动获批。发生范围变化时，仅对受影响部分更新方案并重新提交审阅。

## 执行顺序与越过门禁后的处理

执行顺序固定为：检查现状并判断底层/游戏框架、清溪镇或狼人杀的行为归属 → 在对应层编写/更新note及设计与验收说明（跨层拆分并互链） → 提交具体版本和范围供用户审阅 → 获得明确确认并记录 → 按需建立Git检查点 → 编写行为测试并记录失败 → 实现 → 验证并回填真实证据。测试先行位于方案确认之后，不能以测试先行为理由提前编码。

若发现已经提前生成或修改实现、可执行测试、迁移或部署配置，立即停止该未获确认范围的开发并如实说明。保留现有工作区和Git检查点，不擅自删除、回退或将其当作已批准成果；在所属note区分“提前实现待审阅”“已确认”“未实现”，列出具体文件、影响及已有验证证据，再提交用户决定如何处理。事后补文档、测试通过或已提交Git，均不能追溯替代事前确认。
