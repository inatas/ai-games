# 大改前的Git版本检查点

适用场景：评估或开展跨模块重构、核心流程/数据结构替换、大范围迁移、整体界面重做或实现重写。必须在大改前加载；普通Git查询或同步不因此要求创建检查点。

对当前项目进行较大改动或重写前，必须先将改动前的项目状态提交到本地Git，形成可回退的版本，再开始修改。适用情况包括跨模块重构、核心流程或数据结构替换、大范围目录迁移、整体界面重做及实现重写。此要求由用户明确授权执行，无需为同一范围的本地检查点提交重复请求确认；它不替代[开发方案确认门禁](development-approval.md)。

1. 开始大改前检查仓库状态、已有差异和忽略规则。尚未初始化Git时，在本项目根目录初始化；不得改动上级或其他项目的仓库。已有提交且相关工作区状态完全一致时，可直接记录该提交作为检查点，无需空提交。
2. 检查点应保留当前项目代码、文档、测试和必要配置，包括即将受影响的已有修改；检查并明确选择暂存文件，不覆盖或丢弃用户改动。不得提交.env、模型Key、登录凭据、数据库内容、运行日志、依赖目录或构建产物；可提交不含秘密的.env.example。
3. 提交说明应清楚标明改动前的基线及即将开展的工作。在对应需求note的当前进展中记录基线提交哈希、分支及已运行检查和已知问题；未经验证的基线不得称为稳定版本。
4. 确认提交成功、检查点包含需保留的状态后，才能开始大改。若Git不可用、提交身份未配置或提交失败，先说明具体阻碍并解决；不得虚构身份、静默跳过检查点或在未形成版本时继续重写。
5. 本地提交不等于推送远端，不自动push、改写既有历史或执行破坏性回退。Git仅保存已提交文件；涉及数据库迁移时，还须在设计中说明数据备份与恢复方式，不能用代码检查点代替数据恢复方案。
