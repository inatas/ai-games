## 开发方案 v1.1（2026-09-23，待确认）

用户审阅 v1 后指出公共列不应使用座位号与内部 scope 表示发起人；应以通用 `user_id` 标识真人或 Robot，以 `mod_id` 标识游戏类型，以 `room_id` 标识该 MOD 的游戏实例。已按此修订设计：狼人杀 `room_id` 为对局房间 ID；武侠 `room_id` 为 realm ID。`seat_id`、`scope_id`、phase 等归扩展详情，不作为公共列。因 NPC 和调度器没有用户账号，`user_id` 对这些事件为空，另由通用 `initiator_type` 区分来源，并在详情保存 NPC ID 或系统任务 ID；不伪造用户账号。v1.1 仍待用户审阅确认，未实施。

唯一契约见[统一执行事件日志 v1](../../docs/specs/execution-event-log-v1.md)，验收用例见[EL-01～EL-12](../../docs/testing/execution-event-log-v1.md)。本 note 管公共日志、Harness、回合运行时及持久查询接口；狼人杀无模型审计演示的接入见[本地001](../../mods/werewolf/.agents/note/001-ai-spectator-mvp.md)。

本次范围：PostgreSQL 追加式执行日志；底层统一 `append(tx, event)` 与受信任分页查询；Harness 的准备、模型尝试和结果记录；平台事实事件写入时同步记录其发起与结果；回合房间的登记、脚本/模型提交、默认结算及阶段推进记录；狼人杀使用同一模型上下文装配路径、可控模拟模型完成对局，并提供仅本机可读的审计检查入口。当前平台事实事件、房间可见事件和 `fw_model_calls` 不被改写成日志；日志事件本身不触发游戏消费。明确不包含真实供应商调用、日志前端、跨框架所有历史动作补录、外部分析平台与生产管理员系统。

接口、数据、状态与边界：通用事件信封分离唯一 `eventId` 和稳定 `eventType`，携带 `userId/modId/roomId/requestId`、发生时间、来源类型、结果码及受限 `details` JSON。状态变更与对应提交事件同事务；模型请求发出前后分别记录尝试与输出，失败也能留痕，但不得使失败的游戏状态变为有效。请求幂等键约束重复写入；日志按内部/席位可见/公开分级，原始上下文和原始输出始终内部级，不能出现在旁观、对手上下文或普通游戏历史。密钥和鉴权头不得进入日志。具体表、索引、长度、保留与查询规则见契约。

验收：先写可失败的中性数据库行为测试，覆盖原子提交/回滚、重复请求、多宿主并发、恢复、排序分页、权限和密钥排除；再验证 Harness 记录的是**实际传给适配器的最终 messages**、Schema 和原始返回，不是事后重建摘要；最后在不启用网络模型的狼人杀 Demo 中走一局，导出事件顺序与上下文，检查私密信息水位、调用场景和截止默认。真实 PostgreSQL 与演示证据单列，不以 Mock 代替供应商实测。

实施顺序：用户确认 v1 范围 → 保存当前工作区 Git 检查点（现有未提交改动须保留，密钥与运行日志不提交）→ 中性失败测试 → 通用日志表/API → Harness 与房间运行时接入 → MOD 审计 Demo/检查入口 → 类型、全量回归、真实数据库与全局演示验证。当前只写方案，未改实现、测试、数据库或运行配置，也未发起真实模型调用。
