# 武侠世界示例 MVP 设计

版本：v2，用户已通过“继续代码实现”确认并完成MVP实现。配套[地图表现设计](map-presentation.md)、[测试设计](world-mvp-testing.md)与[实施计划](world-mvp-plan.md)；实际覆盖范围见[验证记录](world-mvp-verification.md)。

## 1. 目标与参考

做一个房间驱动、图形辅助、持续存档的Web武侠世界。玩家在小镇和近郊移动，通过人物与物品完成“探索→打听→找物→交付→行善→拜师→切磋”的循环，并能在后续交互中引用既往经历。

参考北大侠客行的房间导航、NPC交互与学习组织方式：[新手指南](https://wiki.pkuxkx.net/wiki/pkuxkx/guide)、[技能说明](https://wiki.pkuxkx.net/wiki/newbie/skill)。这些来源用于理解玩法结构；以下地图、人物、数值和范围均是本项目的设计，不复刻其世界规模或全部系统。

MVP默认沿用当前每用户一个当前存档：不同用户拥有各自的NPC、任务及物品状态。这里采用MUD的空间与交互形式，尚不是多人共享江湖。多人交易、抢夺、跨玩家战斗与全服事件需要另立需求。

## 2. 三部分职责

| 部分 | 拥有的职责 | 不承担的职责 |
|---|---|---|
| 武侠游戏引擎（示例内部） | 房间图、移动、可见性、角色属性、NPC状态、物品归属、任务状态机、资格与奖励计算 | 不自建模型协议、上下文预算或通用提交协调器 |
| 武侠内容 | 地名、人物背景、地图配置、对白主题、物品、任务、门派设定及视觉模板配置 | 不把题材字段写进框架公共类型 |
| AI Harness公共框架 | 账号会话及当前scope、持续记忆、上下文装配、模型适配、结构校验、幂等与受控事务提交 | 不知道房间如何相邻、谁可拜师、任务是否完成或奖励多少 |

游戏引擎先留在mods/qingxi/src内，按世界查询、行动规则和内容配置区分职责；不先提取通用MUD包或脚本引擎。未来另一款游戏出现实际复用需求时再提取。React呈现位于apps/web，服务器装配位于apps/server；二者中的武侠需求仍由示例note管理。

NPC是持久化的游戏对象。交谈或拜师需要推理时，宿主发起一次模型判定；无需为每名NPC启动常驻Agent。背景事件先作为配置或已提交历史存在，不自动成为Agent。

## 3. Web架构

```text
浏览器 React：局部地图、场景对象、操作面板、角色/背包/任务
       │ HTTP + 会话Cookie；提交后按requestId查询结果
Fastify：身份与当前存档授权、参数校验、宿主装配
       │
武侠宿主：检查资格、读取权威状态、提供上下文、计算与应用结果
       │
AI Harness：记忆、上下文、模型、校验、事务协调
       ├─ PostgreSQL：公共表 + 武侠游戏表
       └─ 服务端模型适配器：Mock / 已配置真实模型
```

保持现有B/S架构和Docker服务划分，不为本MVP增加WebSocket、地图服务、消息队列或浏览器模型Key。移动等确定性动作不调用模型。模型等待期间不持有数据库事务；客户端按钮状态不替代服务端检查。

## 4. MVP必须具备的内容

| 能力 | MVP范围 | 为什么必须 |
|---|---|---|
| 世界与位置 | 1个区域、12个room、显式出口及访问条件、已发现地点 | 让探索与所在位置具有实际意义 |
| 玩家 | 银两、侠义、武学、师承、位置、任务与背包；复用账号和持续存档 | 保存成长及交互结果 |
| NPC | 5名，固定位置、身份、可用动作、与本玩家的交互历史 | 提供可持续交互的对象 |
| 行动契约 | 查看、移动、交谈、拾取、交付、行善、拜师、挑战、奇遇 | 明确每次交互的输入、条件及结果 |
| 物品与背包 | 1种任务物品“药包”，数量与归属由服务器管理 | 验证世界对象到玩家再到NPC的状态流转 |
| 任务 | 1条“寻回药包”，明确状态及一次性奖励 | 提供探索目标与完成反馈 |
| 成长与切磋 | 沿用侠义/拜师/武学成长；单次确定性切磋 | 让行动影响后续资格与结果 |
| AI与记忆 | 按主题交谈、拜师和奇遇的有限结果判定 | 验证历史与当前场景参与推理 |
| Web呈现 | 局部地图、模板场景、对象热点及操作面板 | 无需只靠环境文字和命令输入 |
| 可靠性 | scope隔离、持久化、幂等、失败无部分变化 | 支持长期档案及刷新恢复 |

不加入血量/内力/饥饿、实时战斗、死亡惩罚、装备属性、商店经济、技能树、多人、日夜定时模拟、自由文本自动执行任意动作。任务和物品采用本游戏的简单规则，不建设可视化编辑器或通用任务DSL。

## 5. 地图与人物

下图连线双向；另有茶馆后院→青石街的单向返回出口，用于验证单向拓扑，青石街没有对应反向入口。游戏配置分别声明每个方向的出口，不能依靠画面距离判断可达。武馆后院到内室要求已拜师，其余开放。

```text
村口—青石街—茶馆—茶馆后院
       │
      药铺
       │
      广场—武馆—武馆后院—内室（师承门槛）
       │
      山道—林地—溪边
```

12个稳定roomId由内容配置定义。模板共3类：街巷（村口/街/广场/两处后院）、室内（茶馆/药铺/武馆/内室）、野外（山道/林地/溪边）。

| NPC | 位置 | 交互 |
|---|---|---|
| 店小二 | 茶馆 | 关于本地见闻的主题交谈 |
| 药师 | 药铺 | 打听并接受寻药任务、交付药包 |
| 村民 | 广场 | 行善；回忆玩家此前帮助 |
| 青松道人 | 武馆 | 交谈与拜师 |
| 武馆弟子 | 武馆后院 | 挑战切磋 |

NPC位置在v1固定，不做自主漫游。奇遇通过溪边的“查看旧石碑”设施触发，仍限制每档一次。药包仅在任务进行中且尚未拾取时显示在林地。查看、地图读取不触发模型、不产生游戏事件或版本增加。

## 6. 行动与规则

| 行动 | 前提 | 成功效果 | AI |
|---|---|---|---|
| 移动 | 当前房间有该exitId且满足门槛 | 更新位置与已发现集合 | 无 |
| 交谈 | NPC与玩家同房，选择已配置topicId | 返回合法主题结果，记录交谈事件 | 有 |
| 接受任务 | 在药铺，任务not_started | 状态active | 无 |
| 拾取药包 | 在林地，任务active，背包无药包 | 药包数量1，不可再次拾取 | 无 |
| 交付药包 | 在药铺，任务active，药包数量1 | 移除药包，任务completed，银两+2；奖励仅一次 | 无 |
| 行善 | 在广场，村民在场，银两≥2 | 银两-2、侠义+1；沿用既有开放事项规则 | 无 |
| 拜师 | 在武馆，青松道人在场，未拜师且侠义≥2 | ACCEPT：师承青松道人、武学+1；DEFER：不改属性但提交事件 | 有 |
| 挑战 | 在武馆后院，弟子在场 | 武学≥2胜、银两+3；否则败；均记录事件 | 无 |
| 奇遇 | 在溪边，尚未完成 | GIFT银两+4或GUIDANCE武学+1；标记完成并关闭已有相关事项 | 有 |

挑战沿用当前可重复获奖规则，用于演示，不声称已有经济平衡。移动记录简短事件但不默认送入所有NPC的模型上下文。成功状态变更及交谈、合法落败/DEFER均使hostVersion和memoryVersion各加1；规则拒绝、技术失败不变。

主题交谈由服务端给出允许的answerId集合，模型只选answerId；展示文本由主题模板生成，可插入服务端提供的已知历史摘要。玩家可补充最多200码点文本作为判定输入，不能创建新命令或物品。首版不展示未经约束的模型自由叙事；自然对白生成可另立需求。

## 7. 上下文及执行边界

宿主在prepare中读取一致的游戏快照，提供当前房间、可见对象、交谈目标状态、玩家公开状态、相关任务事实和允许结果；只选择本次必要的NPC历史。世界观每次AI调用必需加入。整个地图、其他用户状态、NPC隐藏秘密、素材坐标不进入公共玩家判定上下文。

v1可使用现有worldview、facts、instructions和记忆筛选接口承载上述内容，不依赖尚未批准的框架011实现。未来采用[Context Composition](../../../docs/specs/context-composition.md)时，房间与NPC数据映射为scene_state/actor_state块；批准本游戏文档不等于批准修改该公共协议。

模型只返回枚举选择，不返回SQL、奖励值或任意操作。框架校验输出结构；宿主validate/apply在最终事务中重验版本、位置、在场关系与业务条件，计算数值。任务、背包、位置、记忆和请求结果必须原子提交。

## 8. 数据与接口契约

静态世界定义使用游戏侧类型化内容配置，包含worldContentVersion、rooms、exits、NPC定义、物品定义、主题和任务定义；所有引用启动时校验，重复ID、悬空出口、未知模板及不可达必需地点均拒绝加载。模板布局坐标与room图连接分别管理。

已实现的持久化数据：

| 数据 | 最小字段/约束 |
|---|---|
| wuxia_characters扩展 | 现有属性 + current_room_id + world_content_version |
| wuxia_discovered_rooms | scope_id、room_id唯一；出生房间默认已发现 |
| wuxia_npc_states | scope_id、npc_id唯一；room_id、状态；v1初始化后位置不自动变化 |
| wuxia_inventory | scope_id、item_id唯一；quantity非负，药包最多1 |
| wuxia_quests | scope_id、quest_id唯一；not_started/active/completed |

所有游戏查询限制已授权当前scope。运行状态引用对应内容版本；v1部署同时保留所支持的旧内容配置，缺失版本拒绝加载，不静默切换旧档内容。世界内容版本与框架上下文版本是不同概念。

保留现有账号、新局及请求查询接口。扩展GET /api/wuxia/games/:id返回一致版本的角色、当前房间、可见对象、出口及门槛、背包、任务、局部地图；返回值不含NPC内部提示或未发现物品。

POST /api/wuxia/games/:id/actions保留requestId、expectedMemoryVersion及现有action/note，按action使用严格字段分支：move附exitId；talk附targetId/topicId；accept_quest及give附targetId/questId，give再附itemId；pickup附itemId；原四动作由服务端映射固定目标并重验所在房间。客户端不能传奖励、状态快照或任意目的roomId。字段全部计入幂等请求内容；多余字段拒绝。登记202、结果查询200沿用现有协议。

预期游戏拒绝原因包括NOT_ADJACENT、EXIT_LOCKED、TARGET_NOT_PRESENT、INVALID_TOPIC、QUEST_NOT_ACTIVE、ITEM_NOT_AVAILABLE、ITEM_REQUIRED、QUEST_COMPLETED；沿用RULE_REJECTED/detail表达。显示操作列表只是提示，伪造请求仍须重新验证。

## 9. 地图与场景呈现

采用三层方向，MVP交付L2房间关系图和轻量L3场景，L1战略图留到后续。React + SVG固定节点布局、平移缩放、方向箭头、当前位置、探索迷雾及封锁提示；场景复用街巷、室内、野外三类模板。具体投影、信息边界、状态刷新、交互和布局以[地图表现设计](map-presentation.md)为唯一正文。

地图显示当前世界状态；持续记忆解释变化的来源。已探索、当前可感知和本次AI允许知道的信息分别计算。服务端只返回局部且经过授权的投影，前端不持有完整地图或NPC秘密。

## 10. 旧档、版本与实施顺序

本次是较大改动。批准后，在任何实现、可执行测试、迁移或界面重做前创建并记录Git基线；部署迁移前备份开发数据库并验证可恢复。Git回退不能自动撤销数据库变化。

旧角色保留账号、属性、师承、奇遇完成标记、开放事项及全部历史；缺少位置的旧角色一次性补到村口，绑定v1内容、初始化NPC和未开始任务及空背包，不制造游戏行动、奖励或版本增长。迁移可重复执行且不重置已有位置。不得强制所有用户开新局。已处理请求保留原结果；processing请求在切换前等待终态或按现有到期恢复流程处理，再暂停接单执行迁移。

分步实施：先地图、位置和持久化，再NPC/物品/任务，再场景呈现，最后接入主题AI与完整验收。每一步先写相应行为测试。现有D-*纯规则与框架F-*继续回归；受房间前提影响的旧Demo集成用例需补足所在房间，不能删除资格断言以求通过。

已确认范围：本文件及配套文档v2，包含独立世界、12房间/5NPC、L2＋轻量L3、受控主题交谈和旧档兼容。后续变化仍需按需求确认流程处理。
