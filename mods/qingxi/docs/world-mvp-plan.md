## 开发门槛

用户确认v2文档范围后才开始代码、可执行测试和迁移。按根目录规则先检查Git状态及忽略文件，创建改动前的本地提交；记录哈希、分支、实际检查与已知问题。不提交密钥、数据库、日志和生成物，不自动push。Git不可用或提交失败时先解决阻碍。

下列阶段按依赖顺序推进。阶段完成意味着对应证据实际通过，不能只以文件生成作为完成。每阶段先写可失败的行为测试，再实现；批准范围内的正常推进无需反复确认，新增范围重新审阅。

## 阶段与交付

| 阶段 | 工作和产物 | 完成标准 |
|---|---|---|
| P0 基线 | Git检查点；核对现有规则/接口及旧档样本；跑现有必要检查 | 提交哈希可查，基线验证及未通过项有记录，未丢用户修改 |
| P1 世界与存档 | 示例内世界配置/校验、房间出口、初始化及兼容迁移、移动/发现 | WM-01～03、14及单向移动WM-18通过；真实测试库验证迁移重复执行 |
| P2 游戏循环 | NPC在场约束、药包、任务、原四动作位置条件及严格输入分支 | WM-04～08通过；游戏变化、记忆和版本原子提交 |
| P3 快照与接口 | 局部地图、场景、玩家一致投影，授权过滤及请求恢复 | WM-12～13、19、22服务端部分通过；浏览器拿不到全图或远端秘密 |
| P4 Web体验 | React/SVG固定节点图、平移缩放、探索/锁提示、三类场景、热点及窄屏交互 | WM-15～16、18、20～22客户端部分通过；每个关键操作可键盘完成 |
| P5 AI接入 | 使用既有上下文接口提供房间/目标/历史；主题枚举输出与模板反馈 | WM-09～11通过；真实模型检查与Mock结果分开记录 |
| P6 整体验收与部署 | 全流程、规模夹具、旧档演练、Docker回归、文档和Quickstart更新 | WM-01～22有证据；相关既有框架/身份/Demo测试回归；部署后旧档与新档可用 |

P1先完成核心规则与测试库迁移，不提前对开发存档执行迁移；P3先验证API投影，再由P4实现页面。P5不等待或顺带实现框架011；若现有公共契约不足，先记录具体缺口并走公共需求确认流程。

## 预期文件职责

- mods/qingxi/src：内容、世界查询与投影、行动绑定、游戏数据迁移；按职责拆现有game.ts，不重写无关框架模块。
- mods/qingxi/tests：规则测试、游戏夹具和地图投影验收；通用数据库工具继续复用tests/support。
- apps/server/src：装配新增游戏接口及一致读取，复用公共身份授权。
- apps/web/src：地图、场景、对象交互、快照刷新及既有登录/请求恢复整合；必要时拆组件，避免为单个示例建设UI框架。
- packages/*：默认复用现有公共入口。任何超出已批准协议的行为调整先记录框架note及设计。

以上是职责计划，不要求预先建立空目录、空类或全部组件骨架。不增加运行时服务或部署依赖。

## 验证与发布步骤

1. 各阶段运行直接相关测试；阶段收尾记录失败已解决还是仍阻碍，不把设计用例标成已通过。
2. 集成测试使用独立随机schema；规模夹具仅放测试环境。最终执行类型/仓库检查、前端构建、Docker测试及关键浏览器流程，记录命令与实际结果。
3. 在隔离数据库用旧格式数据演练迁移和恢复。开发部署前暂停新请求登记，再等待已有processing终结或走既有到期恢复；确认无进行中提交后备份一致数据库状态。
4. 记录基线代码版本、数据库备份位置与恢复验证结果；备份位于受控且不提交Git的位置。部署加法迁移和新应用，验证旧档保留以及新档初始化。
5. 发布失败先停止新写入，再判断可仅切回代码还是需恢复数据库。只有确认旧代码兼容已迁移数据才只回代码；否则在隔离库恢复验证后安排恢复。恢复备份会丢失备份后的动作，须明确受影响范围并取得恢复操作授权，不自动覆盖开发库或删卷。
6. 将实际验证证据、版本及残余限制写入note和验证记录，更新Quickstart以描述已交付行为。

## 范围与待审阅事项

本轮确认对象为世界/地图/测试/计划v2：12房间、5NPC、单用户独立世界、L2＋轻量L3、HTTP刷新、现有模型协议、旧档兼容。L1战略图、天气/势力、NPC自主Agent、自动寻路、推送与编辑器不在本轮实现。

P0～P6的MVP产物已交付：基线提交、世界与存档、游戏循环、API快照、Web地图、AI接入、Docker部署及实际验收记录均已完成。完整浏览器故障注入覆盖仍可扩充，不能将阶段交付解读为所有设备和异常子场景均已自动验证。
