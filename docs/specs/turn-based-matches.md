# 房间制回合游戏框架大纲（架构方向已确认）

归属：[需求019](../../.agents/note/019-turn-based-matches.md)。首个游戏见[狼人杀大纲](../../mods/werewolf/docs/mvp-design.md)。

## 定位

2026-09-20用户明确要求编写基于房间的回合制游戏框架，不强制整合当前MUD框架，最底层统一。本架构方向已确认；具体接口、数据及验收设计尚待补全，不能视为全部实现细节已获批准。

第二层由两种并列框架组成：现有MUD框架，以及独立的房间制回合游戏框架。两者共同使用第一层基础能力，各自拥有运行模型、游戏状态和客户端视图。第三层由具体游戏MOD接入相应框架，狼人杀接入房间制回合框架。

```text
第三层        青溪镇MOD                 狼人杀MOD
                  │                        │
第二层        MUD游戏框架           房间制回合游戏框架
                  └──────────┬─────────────┘
第一层                 统一基础框架
              模型 / 身份与授权 / 存储 / 可靠提交
```

建议独立包packages/turn-based（公共入口@game-ai/turn-based），现有packages/game-systems继续承载MUD能力；包名作为详细设计建议。房间制回合框架不依赖game-systems，不要求ModHost的MUD WorldView、地图房间、NPC表、任务或行为树。两个第二层框架不互相导入；应用层按游戏类型装配。

统一底层意味着复用现有core/model/storage/identity/platform中适用的公共能力，不复制模型适配、scope隔离、幂等和事务机制，也不要求所有游戏启用聊天、队伍或钱包。公共契约若包含MUD专属假设，在后续设计中明确抽离边界及调用方变更；不在底层增加狼人杀角色或回合规则。

这里的房间是承载一局游戏的逻辑房间，不是地图房间或语音房间。MVP只运行一个全AI房间，不引入真人匹配或大厅。

## 核心能力

1. 房间与座位：定义人数、入座状态，全部AI座位配置就绪后自动开局。
2. 对局生命周期：等待、进行、结束及失败状态；保存对局进度，正常重启不重复开局。
3. 回合与阶段：由游戏定义日夜/阶段、发言顺序、行动资格与推进条件。
4. AI角色：每席绑定一个LLM配置，拥有独立身份、上下文和私有记录；相同模型也不共享私有信息。
5. 信息视角：区分公开信息、角色私有信息、阵营信息；服务端构造各角色能看到的上下文。
6. 动作与结算：AI提出行动，游戏规则校验和结算；公共系统保证提交与恢复一致性。
7. 旁观与复盘：进行中只提供公共视角；结束后开放身份与隐藏行动复盘。隐藏数据不能提前发送到浏览器。

## 分层归属

| 层 | 职责 |
|---|---|
| 基础层 | 模型调用、授权、存储、事务及可靠提交 |
| 第二层：MUD框架 | 地图、NPC、任务等现有持续世界能力 |
| 第二层：房间制回合框架 | 独立的房间、座位、对局、阶段调度、AI隔离和记录投影 |
| 第三层：狼人杀MOD | 12人阵容、角色能力、信息规则、投票和胜负规则 |
| 应用装配 | 启动房间、调度对局、提供只读旁观页面 |

## 后续设计事项

狼人杀规则来源已由用户指定，见游戏大纲；后续确定阶段图、接口、数据表、失败恢复策略及验收细节。当前不确定通用DSL、多游戏编辑器或全局框架重写。只提取首个游戏和中性测试实际需要的能力。

验收方向：满员开局、阶段按规则推进、角色信息隔离、同轮未公开选择不泄漏、提交幂等与重启恢复、终局前后旁观权限切换。此处仅为大纲，尚无实现和测试证据。


独立性验收：仅装配统一底层、房间制回合框架和中性测试游戏时即可运行完整对局，不加载MUD框架或创建地图/NPC/任务表；依赖检查禁止两个第二层框架互相引用。现有MUD回归单独验证。


## 按实际需求抽取共用系统

2026-09-20用户明确：背包、道具等将来可能被多个游戏框架使用，出现实际需求后再抽象。当前保留已有系统归属，不为未来复用预先搬迁库存、设计统一道具协议或建立新的公共系统包。后续由多个游戏的具体需求确定共同契约，再决定共享模块的位置；不得让两个游戏框架为复用某个系统而互相依赖。统一底层不等于将所有可设想的共用玩法系统立即下沉。
