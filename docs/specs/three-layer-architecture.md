# 三层游戏平台架构 v2

已确认扩展：[配置驱动运行设计v1](configured-game-runtime.md)涵盖持久事件、角色/NPC共用Action、JSON配置地图与行为树。基础平台拥有事件投递，可选系统拥有共同移动和NPC调度，MOD拥有条件函数、内容及行为配置；下文既有边界保持，新增验收见需求015～018。

用户已确认三层划分并要求最终调整。此文覆盖现有实现的归属；不自动批准角色属性草案005的数值改版。

| 层 | 入口 | 职责 |
|---|---|---|
| 基础平台 | @game-ai/platform，加identity/core/model/storage | realm、角色身份、在线、频道消息、组队关系、钱包账本、授权和可靠提交 |
| 可选游戏系统 | @game-ai/game-systems | 地图、NPC、空间社交策略、任务、库存，以及MUD客户端契约 |
| MOD | mods/qingxi | 内容、游戏规则、任务目标、奖励及系统装配 |

依赖为MOD→系统→平台→core；平台不得引用系统/MOD或查询房间、NPC、任务、库存表。宿主显式调用migratePlatform与migrateGameSystems；storage只负责公共持久化，不依赖上层。旧mud-core包已删除，现有mud_*表名仅为当前命名，不承担兼容职责。

平台角色不要求room_id。房间列及NPC/任务表由系统迁移创建；平台单独迁移后应能运行无地图角色、公共频道、私聊、队伍和钱包。平台注册器只检查身份、配置与行动；系统注册器追加地图/NPC检查。

社交通过服务端SocialPolicy注入附近角色、局部消息接收者、邀请资格及队伍退出后果。平台验证所有接收者属于同realm的活跃角色；客户端不能提供接收者集合。无空间策略时say拒绝，公共chat与tell仍可用。空间策略由系统提供，青溪显式装配。队伍容量是可配置政策，默认4；单人解散沿用既有行为。任务退出后果由系统同事务回调处理，异常时退出和任务变化一起回滚。

IM本轮落实已有角色级频道、私聊、离线持久消息的基础归属；跨realm账号好友、未读游标、群聊管理、屏蔽和推送未在当前产品提供，不以移动模块冒充新增功能。

钱包提供受信任服务端的整数量额账本API，账号钱包与realm角色钱包显式分开，余额不得为负，幂等键相同参数重放、不同参数拒绝，流水不可由MOD客户端直接写入。青溪现有银两规则本轮保留，未来接入账本须明确资产和退款政策。

支付归可选平台集成模块：订单→渠道验证→幂等入账→对账/退款。当前未选择支付渠道、币种、兑换或退款政策，本轮不创建真实充值接口、模拟到账或开放资金入口；独立设计见payments说明。MOD不得验证支付或增发平台充值余额。

库存系统提供按角色隔离的堆叠物品数量与原子增减，MOD定义合法物品、上限和使用效果。青溪药包接入该机制，仅使用game_inventory；不创建或迁移旧库存表。任务沿用当前共享任务流程，归系统层；个人寻药逻辑仍由MOD定义，不强行通用化任务状态机。

## 验收与迁移

- TL-01：基础包依赖/SQL边界静态检查；无地图注册与基础表独立运行。
- TL-02：无地图角色可聊天组队；空间策略保留同房限制；注入异realm收件人拒绝。
- TL-03：退出任务回调与组队同事务回滚，角色重开走相同回调。
- TL-04：钱包归属、并发扣款、防负数、幂等与事务回滚。
- TL-05：库存隔离、防负数、重复初始化不重发物品；全量既有回归通过。
- TL-06：Docker构建、类型与前端构建；空库初始化及重复启动验证后再部署。

未发布阶段允许破坏性升级，旧表、旧API、旧请求格式不兼容。数据库结构变更后显式重建本项目开发库，不在应用启动时自动清库。正常重启保留当前数据；当前版本请求继续严格幂等。代码检查点不保证数据可恢复。游戏规则/奖励数值本轮不变。
